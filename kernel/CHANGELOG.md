# Kernel changelog

Newest first. Each entry: version, what changed, and a **Migration** line only when the operator must do something by hand (the auto-update never changes operator-owned files).

## Unreleased

Compatibility and first-run repair work for the current test candidate. The release number stays unchanged while A/B testing is in progress.

- **Working-copy privacy, stated accurately.** `local_context/README.md` now ships while payload files remain ignored by Git. The OS no longer claims `.gitignore` makes a file machine-private: Dropbox, Drive, backups, mounted workspaces, and other users of the same working copy may still expose it. Bootstrap asks where an answer may be stored before it writes anything sensitive, and session-only is a supported choice.
- **First history means a real restore point.** On a zip-based first run, Bootstrap now commits the untouched starting package before any operator-owned write instead of leaving shipped files untracked after `git init`. It inspects unexpected files before staging, never stages ignored local-context payload, and stays explicit when a safe baseline cannot be created.
- **Private choice does not imply shared consent.** Choosing session-only or `local_context/` no longer leaves room for a derived challenge to slip into `context/company.md` under a broad later approval. Bootstrap must show the exact neutral shared line and receive a separate, specific agreement.
- **Cumulative operator-owned migrations.** `OS-LAYOUT-VERSION` and `OS-LAYOUT-MIGRATIONS.md` give an unversioned or v0.17-era Folder one complete route to the current file layout without replaying release labels. The update routine presents every pending layout entry, preserves operator content, waits for approval, verifies the result, and advances the marker only after the complete migration.
- **Docs and voice aligned.** The start page, manual, host guide, FAQ, and Assistant now match the current Job, Mission, Role, Bootstrap, and storage contracts.
- **One human starting point across hosts.** `START-HERE.md` now contains package setup and the tester route; the temporary root `README.md` has been removed. `CLAUDE.md` and `AGENTS.md` remain thin host pointers to the same `OS.md`, while one explicit first prompt covers Claude Cowork, ChatGPT Work, Codex and hosts that do not recognise either filename. The host guide distinguishes local-folder operation from advisory project uploads.
- **One-screen Executive View.** "Where are things?" now returns a fixed, compact view of decisions needed, handoffs, active Missions, Systems with an explicit reason for attention, and recent Decisions. Every line points to its source. The view is generated from existing records, carries no independent state or opaque health score, and adds a session-change receipt only when something changed.
- **Familiar operator surface.** The first explanation now starts with business functions, projects, recurring processes, responsibilities, company records and audiences. One BoS OS Assistant stays visible throughout and names the current phase; Bootstrap, Mission Runner, Retrospective and specialist prompts remain internal methods rather than a second set of company Routines or a cast of agents.
- **Roles as the automation decomposition.** Every Mission still decomposes into functional Roles. Each Role is a coherent project responsibility with one human accountable owner, an authority boundary and a human-led -> AI-assisted -> AI-run path. Tasks, tools, prompts and AI personalities cannot become Roles; standing records are still earned only when the responsibility recurs.
- **Shared preferences say what they are.** `context/preferences.md` is a non-sensitive Folder default visible to that Folder's audience, not one person's profile. "Keep it brief" changes the session; persisting it requires an explicit request to make it the shared default after the audience is named.
- **Evidence dimensions separated.** Claim status (confirmed, reported, inferred, hypothesis, simulated), source and freshness no longer collapse into one confidence label. Legacy `[unverified]` findings remain readable and translate when touched, with no bulk rewrite.
- **Material decision and action contract.** A consequential choice now shows the decision, recommendation, basis and uncertainty, effect, reversibility and named human owner before approval. Execution returns a short changed/audience/external-action receipt. Routine clarifications remain short.
- **Context-miss learning without auto-memory.** Review now checks whether missing, stale, wrongly scoped or misclassified context made the Mission harder. It records the result in `retro.md` and proposes at most the narrow repair a person can approve; one-off failures stay out of company Context.
- **Repeated explanation as a proposal signal.** When a fact, authority rule, method or interaction default is repeatedly supplied across separate work, the Assistant may propose its narrowest proper home. Repetition never authorises a write or expands the company baseline.
- **Freshness on use.** Volatile Context can carry `Review when:` alongside its date. The Mission checks it only when relying on the claim, avoiding blanket monthly review.
- **Stronger specialist-method boundary.** The template now names when not to use a method, why it was selected, its reads, output, possible changes, decisions it cannot make, evidence standard, reviewer and bounded follow-ons.
- **Optional read-only BoS check.** On request, ten plain-language invariants check ownership, links, derived views, evidence labels, history and version compatibility. It separates deterministic failures from judgment, assigns no health score and makes no repairs.
- **Mission Role Map.** Shape now confirms the functional decomposition through one generated table showing every Role's Mission outcome, human owner, current and target performance, authority boundary and source. It is also available on request, names missing fields instead of guessing and creates no second record.
- **Role Evolution View.** “Where can AI help next?” now produces an on-request view across a Mission, System or the company. It keeps the human owner and authority ceiling visible, moves at most one performance rung at a time, names the evidence or what is missing, assigns no readiness score and changes nothing by itself.
- **AI work stays tied to progress.** Before substantive work in Run, the Assistant states what it is taking on, why it matters, the Mission and Role result it serves, the minimum sources, what counts as done and where it will stop. This is generated orientation inside Run, not a new operator concept or saved file.
- **Mission completion requires progress evidence.** Review now separates outputs from evidence of the intended result and recommends Continue, Re-scope, Stop and Review, or Close and Review. The human Mission owner decides; completed tasks and artefacts never prove the outcome by themselves.
- **One-confirmation Mission continuation.** After an accepted Plan, and on useful re-entry, the Assistant offers to take the Mission as far as it safely can. On yes it works through every eligible item in the existing `Next`, `In progress`, `Blocked` and `Done` status model, continues past item-level blocks when independent work remains, and returns with outputs, evidence and one highest-value ask. Tool needs are identified before relevant current-user connections are checked; connection never creates authority, and consequential action remains with a person.
- **Scheduled execution remains a Routine.** The Assistant can now recognise, plan, configure and execute settled recurring work on a cadence or event without adding an Automation or Agent to the company model. The Routine declares an unattended execution identity, bounded standing authority, source cursor, quiet no-op and failure behaviour. Schedule changes need named-human approval; transcripts remain reported evidence, and external or consequential action still stops for a person.
- **Team collaboration without a second operating model.** Setup records whether each Folder is solo, a GitHub-managed team or a shared copy with one writer at a time. New Mission work gets stable references; `work.md` remains the sole backlog and status record. In GitHub-managed Folders the Assistant hides routine Git mechanics, checks only explicitly linked live delivery evidence at start, resume, status and Done boundaries, and never mistakes a merge for business completion. Shared drives receive no concurrency assurance, and GitHub does not become a general approvals layer.
- **Fresh-session grounding proof.** Bootstrap now offers a new-session check that must recover the company, Folder, current Mission and next decision or work item from their saved source paths without the operator restating them. File creation alone is not called proof, irrelevant Context is not loaded for show, and working-copy-only material remains scoped to the person who stored it.
- **One current statement per confirmed fact.** An authorised replacement updates the Context source that owns it. Version history retains the prior value where supported; without history, the Assistant warns before saving and records the old → new change in its session account. Unresolved disagreements stay visibly sourced and dated, and consequential Decisions retain their own supersession trail.
- **Minimum sufficient context is a measured design principle.** An evaluator-only benchmark now checks required-source recall, forbidden reads, repeated reads, task-context amplification and host token use against a large irrelevant Context file. It adds no runtime object or operator step and is run for release candidates rather than every wording edit.
- **Smaller fixed Assistant context.** The always-loaded Assistant is now a compact source-first router. Executive View, re-entry and State hygiene load through `session-orientation.md`; company record lookup, historical retrieval and growth maintenance load through `record-retrieval.md` only when triggered. A specific request bypasses full orientation.
- **Missing facts stop at their owner.** When the authoritative source lacks a requested value, the Assistant returns `Not recorded` instead of scanning neighbouring Missions, Roles and Context. It expands once only for a direct link, a distinct source the question requires, a known conflict or an explicit exhaustive-search request.
- **File discovery counts as context.** A routed request opens a known path directly or searches one owning directory with a narrow name, ID or date. It no longer inventories the whole workspace, because thousands of filenames consume tokens even when their files stay closed. The benchmark measures and gates this discovery output.
- **Growing records keep bounded routes.** Decisions and Memory gain small indexes, stable record templates and prospective 12 KB rollover. Baseline Context remains concise; archived State partitions by year or month only as it grows. Indexes locate records and never replace the detailed source. Existing files migrate on touch, with no bulk rewrite.
- **Migration:** OS model 0.22 -> 0.23. Apply the single cumulative entry in `kernel/OS-MODEL-MIGRATIONS.md`, including inspection of any existing `context/preferences.md`; remove personal material rather than silently relabelling it. No model data rewrite.
- **Migration:** operator layout 0/unversioned → 1. Follow the cumulative `kernel/OS-LAYOUT-MIGRATIONS.md` entry; no intermediate release labels are required. The OS asks before changing operator-owned files and sets the marker only after verification.
- **Migration:** operator layout 1 → 2. Add the bounded Decision and Memory indexes and growth instructions, preserve all existing content, and split an oversized live record only prospectively or when next touched. No database or new operator concept is introduced.

## 0.21.2
Final hardening + release-confidence pass. Architecture unchanged; no new primitives. Closes the residual reasoning and data-integrity gaps a Markdown behavioural kernel lives or dies on. **OS-model moves 0.21 → 0.22** (an operator with an older `OS.md` will be walked through the change).

- **No diagnostic anchoring in investigations.** When several causes stay materially plausible, the investigation Mission must be scoped to distinguish the live hypotheses ("determine the material drivers and what to address first"), not narrowed onto the operator's proposed solution ("determine whether qualification is the driver"). Narrowing needs evidence. The old worked example, which itself anchored on qualification, is replaced.
- **Source-of-record principle (OS-model 0.22).** New law in `OS.md`: read the source of record before asserting a recorded value (System name → `systems/INDEX.md`; owner/authority → `context/people.md`; Role → `roles/`; mission status → its `mission.md`; System state → its record; preference → `context/preferences.md`). Never reconstruct a recorded value from plausibility. Generalises the "read `systems/INDEX.md` before naming a System" fix. It is the other face of minimum-context, not a licence to load everything.
- **One decision, one yes, clarified.** A Shape checkpoint may summarise already-agreed fields and ask if the whole Mission is right; the rule means one *new* consequential approval per turn (System record, Role promotion, restricted Folder, consequential action), not re-confirming every field. Consent without ceremony.
- **Skipped-version OS-model migration.** New ledger `kernel/OS-MODEL-MIGRATIONS.md` lists every OS-model change. The update routine now applies **all** migrations after the operator's marker, in order, and bumps the marker only after all are made, so an operator jumping several releases is not left half-migrated. Workspace: differing OS-model markers across visible Folders are surfaced before any cross-Folder work.
- **Terminology.** Residual ambiguous lowercase "job" cleaned from the live Mission Runner and manual where it sat next to the formal Job; a committed `eval/v0.21/deterministic-checks.sh` now runs the structural + terminology checks over the live kernel and docs.
- **Migration:** OS-model 0.21 → 0.22. Mirror the new *source-of-record* paragraph into an existing `OS.md` (under *Minimum sufficient context*) and set `OS-model version: 0.22`. The OS detects an old/missing marker, walks `OS-MODEL-MIGRATIONS.md`, names each change in order, and offers to make it with your go-ahead; the marker bumps only when all are done.

## 0.21.1
Remediation + behavioural-validation pass on the 0.21.0 JTBD architecture. No new primitives; the model is unchanged. Tightens the boundaries that a Markdown behavioural kernel lives or dies on.

- **Diagnose is bounded.** Shape and the Assistant now diagnose *far enough to choose the next sensible Mission, not to establish a definitive root cause*. Explicit may/must-not lists; no interrogating to fill a field; no asserting a cause on sparse or unobserved evidence. When the progress is clear but the cause isn't, the OS shapes an **investigation Mission** and records the working diagnosis as a visibly-uncertain hypothesis (grounding model), rather than pretending to have performed an expert diagnosis. New escalation rule for multi-System, sparse-evidence, disputed, or expensive/irreversible situations. Operator-facing language prefers **progress**; "Job" stays the internal recorded label.
- **System template de-duplicated.** The System record had two overlapping derived Role lists (`Roles & capabilities (derived)` and `Roles`); collapsed to one derived view carrying Role link, owner, optional capability, now -> autonomy target, and Guardian inclusion. Removed the ambiguous "the job this System gets done" (Job is reserved for JTBD).
- **Derived-System update loop closed.** Promoting a Role to a durable record updates the derived view of **every System the Role serves**, not only the mission's primary System, consistently across Shape, Retrospective, and Assistant-created lasting Roles. Still manual and explicit; no reconciliation engine.
- **Role accountability wording fixed.** A Role is the accountable unit of execution a human and/or AI is *hired to perform*; the **accountable owner is one named human at every autonomy level**. AI may perform a Role; AI is never the accountable owner.
- **OS.md compatibility check.** `kernel/OS-MODEL-VERSION` plus an `OS-model version:` marker in `OS.md` let the update routine detect an `OS.md` that predates a model migration and tell the operator exactly what to change, without ever rewriting the operator-owned file and without nagging once mirrored.
- **Docs completed.** `OPERATORS-MANUAL.md` and `A-SESSION-WALKTHROUGH.md` reflect Challenge -> Diagnose -> progress -> Mission -> Roles -> Plan/Execute -> Learn, including the investigation-Mission path. Not JTBD training.
- **Migration:** none forced (kernel auto-updates). One operator action if you keep an existing `OS.md`: mirror the model wording (Roles are "hired to perform" with one human accountable owner; the grounding + Diagnose-boundary principle) and add the line `OS-model version: 0.21` near the foot of `OS.md`. The OS will detect a missing/old marker, name the exact change, and offer to make it with your go-ahead. Once the marker reads `0.21`, the notice stops.

## 0.21.0
JTBD architecture: the OS diagnoses before it decides. A challenge in the operator's own words is diagnosed into the Job (the progress they're trying to make), the Mission is the bounded intervention chosen to serve that Job, and every Mission decomposes into the Roles — the accountable units of execution, human or AI — that deliver it. (Worked through as the "v0.19" architecture review; shipped as 0.21.0 in this lineage.)

- **Job, explicit and thin.** Missions carry a two-field Job (circumstance & struggle; progress sought) with a `hypothesis | confirmed` status. "Confirmed" means understood well enough to choose a sensible Mission, not a formal study. The Assistant diagnoses the challenge into a Job hypothesis, one question at a time; Mission Runner Shape settles and records it. A committed mission confirms its Job before going active; an exploration may run on a hypothesis. No global Jobs registry: the Job lives in the Mission.
- **One Roles model.** The old Capability steps + Roles required sections merge into a single `## Roles`. A Role is an accountable unit of execution (who, human or AI, is accountable for an outcome) with an owner, execution mode and authority; named role-like, not as a verb/object task. The reusable capability it instances is an optional descriptor; a novel Role needs none. Mission-local by default; promoted to a durable `roles/` record only when earned.
- **Systems maps are derived.** A System no longer draws a capability pipeline up front; its Roles-&-capabilities map is earned as missions promote durable Roles into it (Shape/Retrospective update it on promotion).
- **BoS knowledge, two touchpoints, no fence.** A client-side contract (`kernel/routines/bos-knowledge.md`) uses broad diagnosis-steered retrieval with a distinctiveness gate and stand-down, at Diagnose and at Role performance; the knowledge service itself stays outside this repo.
- **Grounding.** `OS.md` now requires supplied/retrieved fact vs inference vs hypothesis to stay distinguishable; company-specific facts are never invented.
- **Terminology.** "Job" is reserved for JTBD; Systems and Roles are no longer called "jobs".
- **Migration:** none forced. Kernel routines/templates auto-update; existing missions keep their old Capability steps / Roles required sections and gain a Job only if a human re-shapes them (routines dual-read legacy, no fabricated Jobs). Because `OS.md` is operator-owned, mirror its new model paragraph and grounding principle by hand in an existing install.

## 0.20.0
Decomposition is now the default, for every mission. v0.19 brought systems-thinking back when a mission first touched a System; a live test showed that wasn't enough. If a mission wasn't the first work in its System, or the operator did everything themselves, the OS still fell back to proposing one broad "person does the work" Role. Now every mission decomposes into its capability-steps at Shape, always, even when one person performs them all, because the value is the thinking: seeing the whole machine before you build it, and which steps can be handed to AI later.

- **Mandatory capability decomposition at Shape.** Every mission breaks its work into enduring capability-steps (surface -> qualify -> message -> sequence -> ...), each with who performs it now and its now -> autonomy target. Recorded in `mission.md` (new Capability steps section). Never a single broad Role bucket.
- **Mapping is always; minting is earned.** Standing up a `roles/` record for a step stays the earned move (the durability test), so a mission stands up the one or two records its work actually needs, not the whole pipeline. The decomposition is cheap thinking, not a folder of role files, so no new bureaucracy.
- **Plan executes against the decomposition.** The capability-steps are the enduring machine; `work.md` is the concrete worklist that builds them. Kept distinct.
- **Migration:** none. The routines and the `mission.md` template are refreshed by the auto-update; existing missions gain the Capability steps section as they're next shaped or edited.

## 0.19.1
Plain voice, enforced. The OS was still slipping AI-register words (durable, honest, canonical) into what it said, because the ban lived only in the build process, not in the running OS. Now `OS.md` carries a Voice rule that governs every routine's output, reinforced at the top of the Assistant and Mission Runner: none of the machine-written words, no em dashes, plain founder language, said the way a sharp operator talks.

- **Migration:** the rule ships in the auto-updated routines and the operator-owned `OS.md`; mirror the `OS.md` Voice paragraph by hand in an existing install.

## 0.19.0
Systems thinking, back in the kernel. Removing the Agent primitive (v0.16) was right, but it quietly dropped the OS's job of *decomposing* work. This release brings that back through Roles, not agents: the OS now breaks a System into its composable capability-Roles, each with an explicit human -> AI autonomy path, so a System becomes a foundation you can progressively automate rather than one broad bucket that says who does the work.

- **A System decomposes into a capability pipeline.** When a mission is the first real work in a System, opening its record now includes drawing the System's Roles: the enduring capabilities it breaks into, in pipeline order, each with an owner and a now -> autonomy target. That map is the foundation; individual Role records are still stood up only as work earns them (mapping is not mass-minting).
- **Roles carry a human -> AI autonomy trajectory, first-class.** The Role template gains `How performed: now → autonomy target` (human-done -> AI-assisted -> AI-run with human sign-off). A Role's outcome is a capability, not an activity, and the accountable owner stays a person at every rung.
- **Altitude guard.** A Role is a capability that could be owned and progressively automated, never a person's title or "X does the work". If a proposed Role reads that way, the OS decomposes it further before materialising.
- **The System record holds the capability map.** `systems/<name>.md` gains a `Role decomposition (capability pipeline)` section listing each constituent Role and its current autonomy state.
- **Migration:** none. The routines and templates carrying this are refreshed by the auto-update; existing System and Role records keep working, and gain the new sections as they're next edited.

## 0.18.1
First-run polish from a live onboarding test.

- **One question at a time.** The OS now asks a single question and waits, everywhere. No more stacking two questions, or a question and a confirmation, in one turn. The version-history setup question is handled on its own turn, before the first real question. Locked in as a standing rule in `OS.md` and enforced in Bootstrap.
- **Plainer voice.** Dropped a handful of words that read as machine-written from everything the OS says, in favour of plain language a founder would use.
- **The opening understands you before it asks what you want.** Bootstrap now takes your name and your company, researches the company, and only then asks what you want the OS to help with (a specific challenge, or exploring AI across the business) and your North Star. The old personal-goal question that led with "exit" is gone; it fed nothing downstream and set the wrong tone for a BoS founder's first moment. What you say now directs the first mission, shaped as a commitment or an exploration to match, and it replaces a duplicate ask (the first mission no longer comes from a second "what's most pressing?" at the end).
- **Your candid "why here" stays private.** The new question about what you want the OS to help with can be commercially sensitive, so its answer is written to a new `local_context/` folder that is git-ignored: it stays on your machine and never reaches the shared repo or GitHub. The OS says so when it asks, so you can be direct. `local_context/` is also the home for machine-local pointers that shouldn't travel to the team.
- **Migration (existing installs):** add a git-ignored `local_context/` folder (and a `local_context/` line in your `.gitignore`) for private notes; the release ships `.gitignore` and `local_context/README.md` for new installs. The one-question rule is also added to the operator-owned `OS.md`; mirror that line by hand if you want it stated there.

## 0.18.0
Made real by a regression harness. The v0.17 laws were right; a founder then ran the kernel through six live sessions and the side-notes showed where a first-time operator actually gets lost or stops trusting it. Those sessions became a regression harness (`eval/mark-live-test-2026-09/`), and this release is what the harness demanded, plus a pass through every open design question. The first run is still three questions and a mission; it just guides the operator better and loses nothing over time.

- **Orientation that lands.** Explaining a mode in the abstract doesn't work, even for someone who knows the model; a concrete item does. So the Mission Runner now explains each mode by pointing at this mission's own worklist, not a definition. The first time a kernel word appears (System record, Role, Guardian, Folder) it gets a plain-language aside before it's used as if obvious. Bootstrap and the Mission Runner now set time expectations, per step and per mode.
- **The OS keeps leading.** The Assistant anchors "what's next" in the single biggest challenge the operator named at Bootstrap, names it, and checks it still holds, rather than going quiet with "up to you". An exploration is treated as one channel of a portfolio: the OS asks what the next experiment is rather than stopping at one.
- **Trust that survives time.** Demo or example content is tagged `[simulated]` and surfaced as simulated on every read-back, so a fabricated line can never pass as real work later. Inline citations are checked against their Sources register as files are read, so a dangling reference left by an edit or merge is caught. A finding's age and confidence still travel with it.
- **Nothing is lost.** Pruning `state.md` at session end now **moves** resolved items to a new `archive/` folder instead of deleting them, so a retro months later has the full record. A **session-end commit sweep** commits anything durable left uncommitted, so the audit trail is complete without anyone opening a Terminal.
- **Knowing where you are.** At session open the Assistant names the instance it's reading from and, if it can see a second BoS OS nearby, stops and asks which is live rather than answering from a stale copy. An open handoff shows the mission's owner and the person it waits on as two separate facts, so the owner never misreads it as losing the mission.
- **Self-update tells the truth.** It distinguishes "offline, retry later" from "the source is private or wrong", and never implies the OS is current when the source didn't resolve.
- **Hosts, spelled out.** `docs/HOSTS.md` names Cowork and other mounted folders as their own shape (edit in place, commit from your own Terminal), gives a guided first-time GitHub path with the classic error messages decoded, and explains Dropbox vs git vs GitHub and what you actually lose without a commit (the checkpoint, not the file).
- **Systems you can see.** Each of the eleven Systems now ships a browsable **stub** from day one, so opening `systems/` shows the whole shape of the company, not two files. A stub becomes a full record only when real work earns it, as before.
- **Simpler mission IDs.** A mission folder is now `<FF><NN>_name`: the two-letter initial of its Folder plus a per-Folder number (`CO01_...`, `EX01_...`), tied to its Folder namespace instead of carrying the full Folder word.
- **Built to grow.** A new `kernel/routines/INDEX.md` is the source of truth for the routine set (core plus specialist), so new capabilities ship without editing operator files; a `specialist-routine` template gives reusable expert prompts a shape; and the two ways capability grows are written down: the kernel channel (routines and specialist prompts via auto-update) and the System-package channel (a System like annual planning shipping its own Roles into your space). The two-letter shorthand offer is dropped from Bootstrap's close; the mechanism stays if an operator asks for one.
- **A tidier root.** The human docs are consolidated: `START-HERE.md` is the single entry (the old `README.md` folds into it), and the reference docs (`OPERATORS-MANUAL.md`, `HOSTS.md`, `A-SESSION-WALKTHROUGH.md`, `WORKSPACE.md`, `WORKSPACE-CLAUDE.md`) move into a `docs/` folder, so a new operator opens to five files at the root, not eleven. All of them were refreshed to match this release.
- **Migration (existing installs only):** kernel routines and templates, including the new `INDEX.md` and `specialist-routine.md`, are refreshed for you by the auto-update. By hand, add the operator-owned pieces this release introduces: the eleven `systems/` stub files, and an `archive/` folder (`README.md` and `state-archive.md`). And update the operator-owned `OS.md` shim: add `archive/` to the "yours" list, point its routines line at `kernel/routines/INDEX.md`, add the two-channel note, change the commit-message example from `<SCOPE-NNN>` to `<mission id (e.g. CO01)>`, and repoint its `HOSTS.md` references to `docs/HOSTS.md`. The doc restructure (START-HERE absorbing README, reference docs into `docs/`) is operator-owned too, so existing installs keep their current layout unless you mirror it by hand. Existing mission folders keep their names; only new missions use the new ID form.

## 0.17.0
Every important law now has a lifecycle or a forcing function. The v0.16 model was conceptually right but left the good behaviour to good intentions; a live-system retro found six places where the design was correct but not yet enforced. This release makes them inevitable. The first run is unchanged, and no operator-owned file changes shape on day one.

- **Roles and Systems get a lifecycle.** They were always "earned", but nothing turned earned into materialised. Now the **Mission Runner materialises them at Shape**: when a mission needs a Role with no record and the responsibility is real, it drafts a thin Role inline (Type, a named human owner, a one-line outcome, Authority, an Onboarding read-list), reads it back, and gets one yes before carrying on. First real work in a System with no record offers to open the System record. The rule is **propose, do not silently bureaucratise**. The Assistant does the same outside a mission, and tends what exists (create, change, **merge**, retire); the Retrospective catches a responsibility that ran without an owning Role.
- **Retire is a review signal, not an auto-delete.** Long inactivity prompts the question "does this responsibility still exist?"; a person decides. A quiet System **keeps its record, marked `Dormant`**, and wakes on the next mission that touches it, so references never break.
- **Materialising is audited, not automatically a Decision.** Every materialisation lands in the audit trail; a `decisions/` entry is added only for a genuine organisational choice (a new accountability, a changed owner or authority, standing up a Guardian), so `decisions/` doesn't bloat.
- **State hygiene is now a forcing function, not a hope.** At session end the Assistant prunes **by meaning first**: remove resolved items, promote durable truth to `decisions/` / `memory/` / its source, keep only current exceptions. A **size tripwire is only a backstop**, and its threshold is configurable in `operator-rules.md`, not a fixed number. One-line summaries are bounded to a recent-change window. Where the host keeps no history, hygiene **archives rather than deletes**.
- **Minimum context has a stated fallback.** The principle is always on; only the routing changes with maturity. Before Roles exist, work routes from the Mission's own knowledge, the primary System's strategy and state, and a **bounded company baseline** (the fixed Bootstrap set, never a general read of `context/`). In Advisory mode the OS **names the minimum file set up front** instead of assuming retrieval it doesn't have.
- **Relationship ownership ends cross-link drift.** One relationship has one canonical owner: a Mission owns the Systems and Roles it names; a Role owns the Systems it serves. A System's Missions and Roles lists are **derived views**, reconciled from their owners by the Assistant as it reads, not asserted by hand in both directions.
- **A Guardian and its standard are canonical and live once.** A company-wide Guardian governing private work is **applied in place** across any Folder the current operator can see, never duplicated or shadowed. The standard is referenced, not copied; the Guardian's review notes and gate status stay with the private work, and nothing about it is written back. Permission use case 15 is rewritten to this.
- **Progressive disclosure for Onboarding.** A small Role's Onboarding is a single "Read:" list. The two-tier split (Core knowledge / Know when relevant) is a scaling pattern the Role earns when the list grows, not a required shape. This lowers the day-one concept count.
- **Polished after a real smoke test.** One early mission was run end to end through a fresh instance before release. ## 0.12.0
Two changes, from Mark's first-run feedback.

**Bootstrap is now a cited, document-aware first light.** It asks three opening questions (the two-letter shorthand is dropped from the openers; you can still set one later), and opens by telling you what the whole session will do before the first question. Its research now cites every claim and tags how sure it is (confirmed / reported / inferred), marks gaps as `[NEEDS INPUT]`, then **proactively asks for any internal documents**, mines and cites them, reconciles them against the public draft (a deck keeps its gloss; where internal disagrees with public, both are recorded), and puts the remaining gaps back to you.

**Every durable change is now audited.** Writes still land straight on disk (that's the point), but each durable change (to `context/`, `decisions.md`, `missions/`, `memory/`) is recorded to the version history with provenance (who · routine · mission), the most durable records carry an inline "who changed this" stamp, and you can ask the OS "what changed / who changed X / undo that" in plain language. Trust comes from being able to see and undo, not from approving every write in advance.

**The Assistant is a guide, not a switchboard.** It's now written to coach: guide more for a newcomer or anyone stuck, ease off for the fluent, and never leave you at a dead end. It tells you where you are as you go: the Mission Runner names each mode (Shape / Plan / Run), says what it's for and what's next, and checkpoints before moving on; the Assistant frames every hand-off ("I'll take you to the Mission Runner in Shape mode, that's where we…"). After your first mission, Bootstrap leaves you with two or three concrete next steps rather than a full stop. And you set the pace: say "keep it brief" or "walk me through it" and it remembers.

**Facts now carry their age and confidence.** A finding recorded in a mission (a number, a status that could change) is tagged `[confirmed <date>]` or `[unverified <date>]`, and when a later session reads it back it surfaces the tag rather than stating an old guess as settled fact, so "recorded a week ago, unconfirmed" travels with the claim instead of hardening into truth.

Bootstrap's opening questions are asked as plain open questions, never a multiple-choice prompt. On a brand-new OS the update check says which source it's about to reach out to before it does, and a new FAQ answers "how do I know the update source is really yours?"
